# Notes de version

Toutes les évolutions notables de ha-gazpar-rust sont consignées ici, la version la plus récente en haut.

Le format suit [Keep a Changelog](https://keepachangelog.com/fr/). Les numéros de version sont de la forme `AAAA.M.N` : `AAAA.M` est la version de Home Assistant contre laquelle la version a été validée, `N` le rang de la publication dans cette lignée.

Chaque version publiée a une section dont l'en-tête est exactement `## [AAAA.M.N] - AAAA-MM-JJ` (date de publication), éventuellement suivi des versions de Home Assistant validées ; une préversion s'écrit `AAAA.M.N-alpha.K` (ou `-beta.K`, `-rc.K`) : `make release-check` et la publication s'appuient sur cet en-tête, et le texte de la version GitHub est le contenu de la section, jusqu'à l'en-tête suivant.

## Non publié

## [2026.9.0-alpha.1] - 2026-11-17

Préversion, validée avec Home Assistant 2026.9 et testée contre de faux serveurs GRDF, mais pas encore essayée sur un vrai compte GRDF. Image `ghcr.io/juliensere/ha-gazpar-rust:2026.9.0-alpha.1` (ni `2026.9` ni `latest`). Lancez `ha-gazpar check` avant `run`.

### Nouveautés

- Plan de conception du projet ([PLAN.md](PLAN.md)).
- Licence MIT, notices des projets d'origine ([NOTICE](NOTICE)) et remerciements.
- Commande `ha-gazpar <commande> [options]` avec les commandes `run`, `once`, `check`, `reset`, plus `--help` (seul ou après une commande) et `--version` ; codes de sortie 0 (succès), 2 (configuration ou ligne de commande incorrecte, ou `reset` sans `--yes`), 1 (autre erreur). Les quatre commandes sont opérationnelles.
- Options après la commande, `--option valeur` ou `--option=valeur` : `--config <chemin>`, `--yes` (avec `reset` seulement) et un paramètre par option de configuration, au nom déduit de la variable (`GRDF_PCE` → `--grdf-pce`, `GRDF_PASSWORD_FILE` → `--grdf-password-file`). Option répétée, paramètre vide, option inconnue (avec suggestion) refusés ; `--grdf-password` et `--ha-token` refusés avec un message qui renvoie vers `--grdf-password-file` et `--ha-token-file`. Les erreurs ne recopient jamais une valeur.
- `ha-gazpar reset` sans `--yes` affiche les statistiques qui seraient effacées et sort avec le code 2, sans rien contacter.
- `ha-gazpar once` : un relevé (connexion à Home Assistant, puis à GRDF, import des jours manquants et de la fenêtre de rattrapage), journalisé sous la forme « relevé : 3 jours importés, dernier jour connu 2026-11-13 » (une ligne par mesure si l'énergie et le volume diffèrent) ; code 1 en cas d'erreur, journalisée.
- `ha-gazpar run` : mode démon, un relevé tout de suite puis toutes les `GAZPAR_SCAN_INTERVAL` minutes ; nouvelle connexion à Home Assistant et à GRDF à chaque relevé. Une erreur (GRDF ou Home Assistant injoignable, en refus…) est journalisée (`ATTENTION` pour une panne de réseau, `ERREUR` sinon) et n'avance jamais le relevé suivant ; le démon ne sort pas. Si GRDF refuse les identifiants, plus aucune connexion à GRDF jusqu'au redémarrage, avec une erreur journalisée à chaque intervalle qui explique quoi faire.
- `ha-gazpar reset --yes` : efface les deux statistiques dans Home Assistant, sans contacter GRDF.
- Au démarrage, journal de la version du programme, puis de la version et du fuseau de Home Assistant, avec un avertissement si Home Assistant est antérieur à la version de référence. Date du jour prise dans le fuseau de Home Assistant.
- `ha-gazpar check` valide la configuration, liste d'un coup tous les problèmes et affiche pour chaque option la valeur retenue et sa provenance (défaut, fichier, environnement, paramètre, fichier lu via une variante `_FILE`), secrets masqués ; puis se connecte à Home Assistant (version, fuseau, dernier jour connu de chaque statistique) et simule un relevé (une connexion à GRDF) : derniers jours lus chez GRDF (7 au plus) et ce qui serait importé. N'écrit rien ; code 1 si Home Assistant ou GRDF est injoignable ou refuse.
- Configuration à trois sources, par ordre de priorité : paramètres de la commande, variables d'environnement (`GRDF_*`, `HA_URL`, `HA_TOKEN`, `GAZPAR_*`), fichier `NOM=valeur` désigné par `--config` ou `GAZPAR_CONFIG`, puis valeurs par défaut. Format exact du fichier ([manuel §4.4](docs/MANUEL.md#44-fichier-de-configuration)) : BOM et fins de ligne Windows acceptés, commentaires sur une ligne à part seulement, guillemets appariés retirés, ni échappement ni substitution, `export`, clé inconnue (avec suggestion) ou répétée refusés ; les erreurs citent la ligne et le nom, jamais la valeur. Variantes `_FILE` (chemin absolu) pour les secrets Docker ou systemd : une option et sa variante forment une seule option, la source la plus forte l'emporte entièrement. Exemple dans [.env.example](.env.example).
- Avertissement pour une variable d'environnement inconnue commençant par `GAZPAR_` ou `GRDF_` (faute de frappe probable) et pour un fichier de configuration lisible par le groupe ou les autres utilisateurs.
- Pas d'option de fuseau horaire (celui de Home Assistant sera lu) ni de type de relevé (seuls les relevés informatifs existent) : `GAZPAR_TIMEZONE` et `GAZPAR_CONSUMPTION_TYPE` n'existent pas.
- Préfixe des statistiques réglable (`GAZPAR_STATISTIC_PREFIX`, `gazpar` par défaut ; `sensor.<nom>` pour reprendre des statistiques d'entité existantes).
- `HA_URL` de la forme `ws://hôte:port` : le chemin `/api/websocket` est ajouté s'il manque ; `wss://` refusé avec un message explicite (seul `ws://` est pris en charge).
- Journal horodaté sur la sortie d'erreur, niveaux `info` et `debug` (`GAZPAR_LOG_LEVEL`).
- Harnais de développement (`make check`, `test`, `lint`, `deny`, `crates`, `deps`, `cover`, `release`…), politique de dépendances (`deny.toml`) et inventaire des dépendances ([DEPENDENCIES.md](DEPENDENCIES.md)) : 3 dépendances directes, 29 crates, plafond 32.
- Intégration continue GitHub Actions : `make check` à chaque push et pull request, compilation statique x86_64 avec taille du binaire, vérification hebdomadaire des avis de sécurité ; Dependabot limité aux mises à jour de sécurité.
- Client WebSocket minimal pour Home Assistant (RFC 6455, bibliothèque standard uniquement) : poignée de main vérifiée, messages fragmentés, réponse aux `ping`, fermeture propre, messages reçus plafonnés à 16 Mio, délais de connexion, lecture et écriture.
- Client des statistiques long terme de Home Assistant : authentification par jeton (jamais journalisé), version de HA annoncée, lecture des points quotidiens, import par lots de 500 points avec minuit dans le fuseau fourni, celui de Home Assistant (heure d'été comprise), effacement.
- Lecture des relevés informatifs de GRDF : un relevé par jour gazier, valeurs exactes au millième, jour sans donnée conservé sans valeur (jamais 0), relevé invalide ignoré avec un avertissement. Jeux d'essai repris de PyGazpar.
- Client HTTP vers GRDF : bocal à cookies maison (domaine, chemin, expiration, `Secure`), redirections suivies à la main avec cookies captés à chaque saut, délais de 10 s (connexion) et 60 s (lecture), taille des réponses bornée ; aucune adresse complète, aucun cookie dans les journaux et les erreurs.
- Client Mon Espace GRDF : connexion Okta comme PyGazpar (une seule tentative, motif du refus sans aucun secret), vérification que le PCE appartient au compte, relevés demandés par fenêtres d'au plus 365 jours pour obtenir tout l'historique, reprises sur 429 (`Retry-After` plafonné à 60 s), page d'erreur ou coupure réseau (3, 6, 12 s), une seule reconnexion si la session expire.
- Faux serveur GRDF pour les tests (flux de connexion, liste des PCE, relevés, pannes pilotables), sans aucun accès au vrai GRDF.
- Essais de bout en bout du binaire, hors ligne, contre les faux GRDF et Home Assistant : `once` deux fois de suite (le second n'écrit rien), jour publié en retard rattrapé, `check` sans écriture, `reset` avec et sans `--yes`, mot de passe refusé (une seule tentative, aucun secret dans la sortie), `run` qui reste en marche. `make dev` lance `check` puis deux `once` contre ces faux serveurs et affiche les sorties.
- `make ha-up` / `make ha-down` : Home Assistant jetable en conteneur (image `ghcr.io/home-assistant/home-assistant`, version de référence 2026.9 ou `HA_TAG=stable`) sur `127.0.0.1:8124`, fuseau `Europe/Paris`, utilisateur et jeton de test créés au démarrage par l'API d'onboarding (aucun secret commité), jeton renouvelé à chaque `make ha-up`.
- `make test-ha` : essais contre ce Home Assistant jetable (import et relecture autour des changements d'heure, statistique externe `gazpar:` et d'entité `sensor.` en source `recorder`, remplacement d'un point, effacement, `kWh` et `m³`, version de HA, regroupement par jour dans le fuseau de HA).
- Intégration continue : essai réel contre Home Assistant 2026.9 à chaque push, et chaque semaine contre `home-assistant:stable` avec ouverture d'un ticket (sans doublon) en cas d'échec.
- Algorithme d'un relevé : lecture préalable de Home Assistant, un seul appel à GRDF pour les jours manquants et la fenêtre de rattrapage, cumuls recalculés à partir du point précédant la fenêtre, jours sans valeur jamais importés, seuls les points modifiés réécrits (deux relevés identiques n'écrivent rien), simulation sans écriture pour `check`.
- Fuseau horaire des jours lu dans Home Assistant (`get_config`) à chaque connexion, avec une base de fuseaux embarquée ; fuseau inconnu signalé clairement. Comparaison de la version de Home Assistant avec la version de référence.
- Requêtes vers GRDF limitées à `grdf.fr` et ses sous-domaines : une redirection ou un lien de fin de connexion vers un autre hôte est refusé, sans être suivi ni réessayé.
- Image Docker minimale pour `linux/amd64` et `linux/arm64` (Raspberry Pi 64 bits) : `FROM scratch`, le binaire statique seul (ni shell, ni certificats, ni base de fuseaux), utilisateur non root par défaut, `ha-gazpar run` lancé par défaut, aucune variable de configuration dans l'image. `make image` (architecture locale), `make image-all` (les deux), `make dist` (binaires statiques extraits et `SHA256SUMS`) ; l'intégration continue construit l'image amd64 et la lance.
- Publication à la pose d'un tag `vAAAA.M.N` : vérification que le tag, la version de `Cargo.toml`, `HA_VERSION` et une section datée de ce fichier concordent (`make release-check`, utilisable en local), `make check`, image multi-architecture poussée sur `ghcr.io/juliensere/ha-gazpar-rust` (étiquettes `AAAA.M.N`, `AAAA.M` et `latest`, les deux dernières seulement pour la version la plus récente) avec provenance, SBOM et attestation signée, puis version GitHub dont le texte est la section de ce fichier, binaires statiques amd64 et arm64 et `SHA256SUMS` joints.
- Refus des identifiants par GRDF distingué des autres échecs de connexion : seul un refus clair d'Okta (mot de passe faux ou compte inconnu : 401 à l'étape du mot de passe, ou clé de refus dans le message d'Okta) donne « connexion à GRDF refusée » ; une panne du service de connexion, une session de connexion expirée ou une étape inattendue donnent « échec de la connexion à GRDF » et restent des erreurs passagères.
- Intégration continue complétée : couverture des tests (seuil de 90 % des lignes, 98 % mesurés), plafond de taille du binaire statique (3 Mio), refus d'une pull request qui modifie `src/` sans mettre à jour ce fichier.
- Journal de diagnostic (`GAZPAR_LOG_LEVEL=debug`), pour comprendre après coup un échec de connexion à GRDF sans rien divulguer : chaque requête (méthode, hôte:port, chemin sans requête, statut ou cause de l'échec, durée, noms des cookies envoyés), chaque redirection (hôte et chemin visés, rang du saut), chaque cookie reçu (nom, domaine ou hôte seul, chemin, ou motif du refus ; jamais la valeur), l'étape de connexion atteinte et les étapes proposées par Okta, puis pour chaque fenêtre de relevés les dates demandées, le nombre de jours reçus, le premier et le dernier, et si le jour `dateFin` figure dans la réponse. Commandes envoyées à Home Assistant avec leur durée. Le niveau `info` est inchangé.
- `make dev` montre aussi un relevé au niveau `debug` et une panne de chaque famille (identifiants refusés, service de connexion en panne, GRDF ou Home Assistant injoignable, reprises, jeton refusé, adresse qui n'est pas Home Assistant).
- Messages d'erreur de l'API GRDF : chaque erreur nomme l'appel (« GRDF, liste des PCE », « GRDF, relevés du 2026-10-18 au 2026-11-16 »), puis la cause en français avec l'hôte et le port visés, jamais l'adresse complète : statut HTTP, page HTML au lieu de JSON, débit limité (avec `Retry-After`), délai de connexion ou de lecture dépassé, connexion refusée, hôte introuvable par le DNS… Après les reprises, l'erreur précise « abandon après 4 tentatives ». Les préfixes techniques « HTTP : » et « API GRDF : » disparaissent. Un PCE absent du compte invite à vérifier `GRDF_PCE`.
- Messages d'erreur de la connexion à GRDF : chaque erreur nomme l'étape (« GRDF, connexion 3/5 (identification Okta) », de 1/5 page d'accueil à 5/5 fin de connexion), le statut HTTP, l'hôte et le port qui ont répondu, et ce qu'Okta dit : textes (`messages`, à défaut `errorSummary`) entre guillemets et codes (`i18n.key`, `errorCode`) entre crochets, expurgés des secrets. Un refus des identifiants s'écrit « identifiants refusés par GRDF (…) ; vérifiez GRDF_USERNAME et GRDF_PASSWORD » ; les préfixes « connexion à GRDF refusée : », « échec de la connexion à GRDF : » et « protocole : » disparaissent.
- Messages d'erreur de Home Assistant : chaque erreur nomme l'hôte et le port, puis l'étape (« Home Assistant (192.168.0.10:8123), connexion TCP », « poignée de main WebSocket », « authentification », « lecture du fuseau horaire (get_config) », « lecture de … du … au … », « import de N points dans … », « effacement de … », « fermeture de la connexion ») et la cause en français (connexion refusée, délai dépassé, hôte introuvable par le DNS, réponse HTTP reçue au lieu de la poignée de main, message et code d'erreur de Home Assistant, raccourcis). Quand l'utilisateur peut agir, la ligne le dit : vérifier `HA_URL` (connexion ou poignée de main), créer un nouveau jeton (`HA_TOKEN` refusé), donner les droits d'administrateur (code `unauthorized`). Les préfixes « entrée-sortie : » et « Home Assistant : » disparaissent.
- Reprises lisibles : chaque nouvel essai d'un appel à GRDF est journalisé « GRDF, relevés du … au … : tentative 1/4 échouée, <motif> ; nouvel essai dans 3 s », et une session expirée « session expirée (statut HTTP 401, hôte:port) ; reconnexion à GRDF (une seule par appel) ». En mode `run`, une panne passagère se termine par « panne passagère, nouvel essai au prochain relevé, dans N min » ; avec `once`, par « panne passagère, relancez plus tard ».

### Corrections

- `HA_URL` est vérifiée dès la configuration par le même analyseur d'adresse que la connexion : un port invalide (`ws://ha:abc`), une adresse IPv6 mal formée, un espace, une requête (`?`) ou un fragment (`#`) donnent une erreur de configuration (code 2) au lieu d'un échec à la connexion (code 1, retenté toutes les `GAZPAR_SCAN_INTERVAL` minutes par `run`).
- Message d'erreur « GRDF injoignable » sans double préfixe après les reprises.
- Un échec de l'étape du mot de passe qui n'est pas un refus (service de connexion indisponible, statut 503 ou 429, session Okta expirée) n'est plus annoncé « mot de passe refusé par GRDF » : le message dit « service de connexion indisponible », « débit limité par GRDF », « session de connexion Okta expirée » ou « réponse inattendue d'Okta ». La classification est inchangée : ce n'est pas un refus des identifiants, et `run` réessaie au relevé suivant.
